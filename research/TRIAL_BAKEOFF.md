## The harness — read this before believing any number below

### The app under test (MEASURED)

`/Users/arjun/bakeoff/app/server.mjs`, zero dependencies, served on `http://127.0.0.1:4380`.
Four pages: `/` (a product + "Add to cart"), `/cart` ("Proceed to checkout"), `/checkout`, `/login`.

**The planted bug**: `/checkout` always renders

```html
<p class="err">Something went wrong. Your order was not placed.</p>
```

Every tool gets the same sentence — *a shopper can check out* — against the same bug. The question
is not whether they find it. A 200-response page that says "Something went wrong" is easy. The
question is **what a developer reads at 2am when it fails**, which is the thing this bakeoff exists
to measure and the thing our prior research assumed rather than checked.

### The model problem, stated plainly

**There is no `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` on this machine** (MEASURED:
`env | grep -iE 'ANTHROPIC|OPENAI'` returns nothing but `CLAUDE_CODE_EXECPATH`). Every tool here is
an LLM loop. So each tool was run in **two passes**:

1. **The cold pass** — exactly what a developer typing the install command hits, with nothing
   configured. This needs no key and is 100% MEASURED. It is also, per `GRAVEYARD_AND_BUYER.md` §4,
   the pass that decides whether evaluation ever happens.
2. **The scripted pass** — a local HTTP server at `http://127.0.0.1:4390/v1`
   (`/Users/arjun/bakeoff/model/server.mjs`) that speaks **both** OpenAI `/v1/chat/completions` and
   Anthropic `/v1/messages`, logs every request, and returns responses I authored to play a
   competent model. This is the same technique our own `test/flake.test.mjs` uses to test the runner
   without spend.

**What the scripted pass legitimately measures**: the real browser, the real DOM/a11y extraction,
the real tool loop, the real assertion plumbing, the real reporter, the real exit code, the real
number of round trips, the real bytes on the wire, and — the point of the exercise — **the real
failure rendering**. That output is generated by their code from a genuine failing page.

**What it does not measure**: model quality. A weaker model than the one I played would fail more
often, and no tool here is credited or debited for that.

Every "the failure output" quote below is verbatim from a terminal on this machine.

## 1. auto-playwright (MIT) — **does not import**

`auto-playwright@1.16.1`, installed 2026-08-30. `npm install auto-playwright @playwright/test openai`
→ **6.6s**, 63 packages, **5 vulnerabilities (1 moderate, 4 high)** (MEASURED, `/tmp/install-autopw.log`).

### The cold pass: it is broken on npm

The documented usage is `import { auto } from "auto-playwright"`. That line does not work:

```
Error: Cannot find module '/Users/arjun/bakeoff/autopw/node_modules/auto-playwright/src/index.ts'.
Please verify that the package.json has a valid "main" entry

   at checkout.spec.ts:2

  1 | import { test } from "@playwright/test";
> 2 | import { auto } from "auto-playwright";
    | ^
Error: No tests found
```

**MEASURED root cause**, from the installed `package.json`:

```json
"files": ["dist"],
"main": "./src/index.ts",
```

The package publishes `dist/` and points `main` at `src/`, which it does not publish. **The
published artefact cannot be imported by its own name.** The workaround is
`import { auto } from "auto-playwright/dist/index.js"`, which no README tells you.

**CONTRADICTS PRIOR RESEARCH.** `FIELD_AGENT_FIRST.md` (line 770, line 887) records
auto-playwright as "the fourth zombie" — MIT, 846★, **13,207 npm downloads/week**, last push
2025-07-08 — and treats the download number as the interesting anomaly. It is worse than dormant:
**13,207 people a week are installing a package that throws on the first import.** That number is
now positively proven to be robots and lockfiles, not users. `RED_TEAM.md` §2.3 argued "npm
downloads measure curiosity, not use". This is the hard proof of that argument, and it should be
promoted from an assertion to a MEASURED fact.

### The failure output (MEASURED, scripted pass)

With the import hand-fixed, a browser installed, and the scripted model at the base URL:

```
  ✘  1 checkout.spec.ts:6:5 › a shopper can check out (454ms)

  1) checkout.spec.ts:6:5 › a shopper can check out ──────────────────────────────

    Error: order was not confirmed: false

       9 |   await auto("click Proceed to checkout", { page, test }, opts);
      10 |   const ok = await auto("Does the page confirm the order was placed?", { page, test }, opts);
    > 11 |   if (ok !== true) throw new Error(`order was not confirmed: ${JSON.stringify(ok)}`);
         |                          ^
        at /Users/arjun/bakeoff/autopw/checkout.spec.ts:11:26
```

**Read this carefully, because it is the single most useful thing in this document.** Every word of
diagnosis in that output is *mine*. `order was not confirmed` is a string I typed into the spec
file. auto-playwright's entire contribution to the failure is the token **`false`**.

Its assertion API returns a boolean. There is no reason, no observed text, no URL, no step trace,
no screenshot. The page said *"Something went wrong. Your order was not placed."* — the model read
that sentence, and the API's shape threw it away before it could reach the developer.

The only real diagnosis on screen comes from **Playwright**, not auto-playwright, in
`test-results/…/error-context.md`:

```yaml
- heading "Checkout" [level=1] [ref=f2e6]
- paragraph [ref=f2e7]: Something went wrong. Your order was not placed.
```

That file exists because Playwright 1.62 writes it for every failure. It would be there if
auto-playwright had never been installed.

### What it cost (MEASURED)

- **10 model round trips** for 3 `auto()` calls (4 + 4 + 2), counted at the server.
- **10,614 bytes of tool-schema JSON on every single call** — 36 function definitions, resent in
  full each round trip. ~106 KB of schema for one three-step test, before any page content.
- Total request size, call 1: 13,181 bytes, of which the actual page snapshot was 1,108.
- Wall clock with a local model: **454 ms**.

### What it wrote into the repo

Nothing. It has no init, no config, no state directory. `test-results/` is Playwright's.

### Verdict

Not a competitor. It is a dead package that does not import, and if it did, its API is
architecturally incapable of explaining a failure because its assertion return type is `boolean`.
Its 13k weekly downloads are the strongest available evidence that **npm downloads in this category
are noise**, which matters for how we read Midscene's and Shortest's numbers too.

## 2. Midscene.js (MIT, ByteDance web-infra) — **the best failure line in the field, and the most expensive way to produce it**

`@midscene/web@1.12.2`, installed 2026-08-30. `npm install @midscene/web playwright` → **39.1s**,
**156 MB of `node_modules`** (MEASURED, `du -sh`).

### The cold pass: a good error buried under 65 lines of its own guts

With no model configured, `npx playwright test` prints **66 lines before the first test result**
(MEASURED, `awk '/✘/{print NR}'`). The first 60 of them are this, dumped as a raw JS object with
internal `Symbol(step)` state, `TestStepInfoImpl`, `boxedStack`, `stepId: 'pw:api@42'`:

```
Midscene - Failed to add base-select appearance style: page.evaluate: Execution context was
destroyed, most likely because of a navigation
    at injectStyle (…/@midscene/web/src/puppeteer/base-page.ts:1595:54)
    at forceChromeSelectRendering (…/base-page.ts:1617:8)
    …
  log: [],
  name: 'Error',
  Symbol(step): {
    location: { file: '…/base-page.ts', line: 1595, column: 54, function: 'injectStyle' },
    …
```

This is **non-fatal cosmetic housekeeping** — it is trying to restyle `<select>` elements and the
page navigated underneath it. It fires on every single run of this app, which has no `<select>` at
all. Then, underneath the wreckage, the actual configuration error, which is genuinely well-written:

```
Error: Model configuration is incomplete: model name (MIDSCENE_MODEL_NAME) is required.
See https://midscenejs.com/model-strategy.html
```

Names the exact variable, links the exact doc. That is the standard. It is just invisible.

### The failure output (MEASURED, scripted pass) — the best in this bakeoff

```
  ✘  1 checkout.spec.ts:3:5 › a shopper can check out (1.6s)

  1) checkout.spec.ts:3:5 › a shopper can check out ──────────────────────────────

    Error: Assertion failed: the page confirms the order was placed
    Reason: The screenshot shows a page headed "Checkout" with a red-bordered paragraph reading
    "Something went wrong. Your order was not placed." and a "Back to cart" link. There is no
    order number, no confirmation heading and no success message anywhere on the page, so the
    statement is false.
        at Insight.aiAssert (…/@midscene/core/src/agent/insight.ts:149:15)
```

**This is the shape to beat.** The sentence you wrote, then a reason in prose that quotes the
page. Compare auto-playwright's `false`.

**The honest caveat, which matters for what we conclude.** That `Reason:` is the model's
`<observation>` field passed through verbatim — I authored it in the scripted pass, so its *prose
quality* is mine, not theirs. What is **theirs, and MEASURED, is the plumbing**: their assertion
prompt has an `<observation>` field at all, and `insight.ts` carries it into the thrown error
instead of discarding it. auto-playwright's prompt has nowhere to put a reason and its API returns
`boolean`; Midscene's has a channel for it and uses it. **That design decision is the whole
difference and it is real.**

There is a second, sharper MEASURED finding in the same code path. On an earlier run my scripted
model returned the wrong XML shape, and Midscene rendered it as:

```
    Error: Assertion failed: the page confirms the order was placed
    Reason: XML parse error: Missing required field: data-json
```

**Midscene reports its own parse failure as "Assertion failed".** A model formatting glitch — a
tool fault — reaches the developer wearing the words that mean *your app is broken*. This is
precisely the distinction our runner spends a whole status on (`errored` = "our side, not your
app", `SCORECARD.md` row 2). Midscene has no such separation. At 2am, "Assertion failed" sends you
to the checkout code; the bug was in the LLM's punctuation.

### What it cost (MEASURED at the wire)

One three-step test, uncached:

| call | bytes | system prompt | base64 screenshot |
|---|---|---|---|
| 1 | 50,991 | 31,124 | 18,463 |
| 2 | 55,926 | 31,124 | 22,667 |
| 3 | 55,201 | 31,124 | 22,667 |
| 4 | 63,558 | 31,124 | 30,271 |
| 5 (assert) | 33,865 | 2,684 | 30,271 |
| **total** | **259,541 bytes** | | |

**~260 KB on the wire for one three-step test**, of which **124 KB is the same 31,124-character
system prompt resent four times** and **124 KB is base64 PNG**. At a conventional ~4 chars/token
that is roughly **65,000 input tokens for one test with three steps** (INFERRED from the MEASURED
byte counts). `FIELD_AGENT_FIRST.md` carried a REPORTED "114K tokens/test via Playwright MCP" as
the cautionary number; this is the same order of magnitude, now MEASURED directly, for the tool the
prior research named the strongest free alternative in existence.

### The cache — and the thing prior research got half right

`MIDSCENE_CACHE=1` produces `midscene_run/cache/checkout.spec.ts(a-shopper-can-check-out).cache.yaml`
in the repo. Contents, verbatim:

```yaml
midsceneVersion: 1.12.2
cacheId: checkout.spec.ts(a-shopper-can-check-out)
caches:
  - type: plan
    prompt: click the Add to cart button
    yamlWorkflow: |
      tasks:
        - name: click the Add to cart button
          flow:
            - aiTap: ''
              locate: the "Add to cart" button
  - type: locate
    prompt: the "Add to cart" button
    cache:
      xpaths:
        - /html/body/form[1]/button[normalize-space()="Add to cart"]
```

**MEASURED: uncached run = 9 model calls. Cached run = 1 model call, 33,865 bytes.** The cache
holds only `plan` and `locate` entries. The assertion is never in it.

**REFINES PRIOR RESEARCH.** `FIELD_AGENT_FIRST.md` (line 700) corrected itself to say Midscene
*does* own the portable-local-artefact property that I had claimed nobody had. That correction is
right about the file and wrong about what the file can do, and the difference is the whole of
`SCORECARD.md` row 4. The decisive test, run twice today:

- **Cache file fully populated, `MIDSCENE_MODEL_NAME` and friends unset:**

  ```
  Error: Model configuration is incomplete: model name (MIDSCENE_MODEL_NAME) is required.
  1 failed
  ```

- **Same cache, model reachable: 1 call, 33,865 bytes** (a 30 KB screenshot to answer one boolean).

**Midscene's cache is a plan cache, not a replay.** It cannot execute a single step without a live
model connection, and it bills a full vision call for every assertion on every run forever. Ours
replays the whole test — assertion included — with **zero** model calls and no key present at all
(§7 below runs it that way). The artefact-you-own row stands; the run-it-offline row does not
transfer to them.

Also worth noting: the cached locator is an **absolute XPath** —
`/html/body/form[1]/button[normalize-space()="Add to cart"]`. Wrap that button in one `<div>` and
the cache misses.

### What it wrote into the repo (MEASURED)

```
midscene_run/report/*.html      — 2.6–2.9 MB per run, one file per run, never pruned
midscene_run/log/*.log          — 13 separate log files
midscene_run/cache/*.cache.yaml — the plan cache
```

**14 MB of `midscene_run/` after five runs of one three-step test** (MEASURED, `du -sh`). The HTML
report is genuinely good — a visual step-by-step with the screenshots embedded — and it is
2.8 MB of embedded base64 every time, in your working tree, with no retention policy.

### Verdict

Midscene is the real thing and the prior research was right to call it the strongest free
alternative. **Its failure line is the target we should be measured against**, and we should copy
the one design decision that produces it: give the assertion a prose-reason channel and carry it
into the error. Its weaknesses are structural and not fixable by effort: ~260 KB per test on the
wire, a cache that still needs the model, no separation between "your app failed" and "our parser
failed", and 2.8 MB of report per run in your repo.

## 3. Shortest (Antiwork, MIT) — **a good report that cannot fail a build**

`@antiwork/shortest@0.4.9`. `npm install @antiwork/shortest` → **24.7s**, 260 packages,
**8 vulnerabilities (4 low, 4 moderate)** (MEASURED).

### The cold pass

`npx shortest init` in a non-TTY shell — which is every CI job — crashes:

```
✖ [🧪 Experimental Next.js] Confirm sample test file generation [FAILED: User force closed the prompt with 0 null]
node:internal/process/promises:324
    triggerUncaughtException(err, true /* fromPromise */);
    ^
ExitPromptError: User force closed the prompt with 0 null
    at file:///…/@inquirer/core/dist/esm/lib/create-prompt.js:57:20
```

**and exits 0** (MEASURED, `echo $?` → `0`). An uncaught exception reported as success. That is a
foreshadowing, not a footnote — see below.

With no key, the config error is short and correct, though it names no environment variable:

```
ConfigError Invalid shortest.config
ai.apiKey: Required (received: "undefined")
```

### Two bugs found in ninety seconds of use

**1. The default test pattern globs `node_modules`.** The shipped default is `**/*.test.ts`, with no
exclusion. On this project — which contains exactly **one** test file:

```
Found 141 test file(s)
❯ checkout.test.ts (1)
…
✘ [ERROR] Could not resolve "vitest"

    node_modules/zod/src/v3/tests/void.test.ts:2:29:
      2 │ import { expect, test } from "vitest";
```

MEASURED: `find node_modules -name "*.test.ts" | wc -l` → **140**. It tried to compile and execute
zod's own unit tests as end-to-end browser tests.

**2. It hands the model a `bash` tool by default.** MEASURED from the wire — the tool list on every
call is `computer, bash, check_email, github_login, navigate, run_callback, sleep`, and the system
prompt says *"You have access to a bash tool to execute bash commands… ensure they are appropriate
for the operating system you are currently using: darwin."* An end-to-end testing framework grants
the LLM arbitrary shell on the developer's machine, on by default, undocumented at the call site.
Nothing in `FIELD_AGENT_FIRST.md` §"data safety" caught this; it is a larger hole than the
seed/teardown gap that section is about.

**3. The model is pinned to `claude-3-5-sonnet-20241022`** (MEASURED from the request body) — a
model shipped in October 2024, hardcoded, in a package whose last commit was 2026-05-21.

### The failure output (MEASURED, scripted pass) — second best in this bakeoff

```
❯ checkout.test.ts (1)
  ● a shopper can add the Blue Widget to their cart, proceed to checkout, and see the order confirmed
    ✗ failed
    ↳ 7,560 tokens (≈ $0.03)
    Reason: The checkout page shows "Something went wrong. Your order was not placed." instead of an order confirmation.
  ⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯

   Tests          1 failed | 0 passed (1)
   Duration       7.13s
   Started at     11:06:14 AM
   Tokens         7,560 tokens (≈ $0.03)
```

Clean. The sentence, the verdict, a reason that quotes the page — **and the token cost and dollar
cost printed next to the test that spent it.** Nobody else in this bakeoff does that, we do not do
that, and it is the single cheapest idea worth stealing from this entire exercise.

One design limit, MEASURED from their system prompt: *"For failures, provide a maximum 1-sentence
reason."* The ceiling on their diagnosis is written into the prompt.

### The disqualifying finding

```
$ npx shortest ; echo "EXIT CODE = $?"
    ✗ failed
   Tests          1 failed | 0 passed (1)
EXIT CODE = 0
```

**MEASURED, reproduced twice. A failing Shortest test exits 0.** In CI the job is green. The
beautiful report scrolls past in a log nobody reads, and the broken checkout ships.

This is the row that decides the tool, and no amount of report polish survives it. Note the shape
of the mistake, because it is the exact contract our `bin/smolanalytics.mjs` protects with a
comment block (*"NOTHING THAT ESCAPES HERE MAY EXIT 1"*) and `suite.test.mjs`/`flake.test.mjs`
assert on: `exitCode()` → 1 only for a real failure, 2 for our own faults, 0 for pass and flaky.
Shortest has the good report and not the contract; a test runner that cannot redden a build is a
logging library.

### The cache

`.shortest/cache/<runId>.json` plus a directory of PNGs per run. MEASURED: running the same failing
test twice made **4 model calls both times**, `"executedFromCache": false`, and reported the same
7,560 tokens. **There is no replay for a failing test** — the run that costs you money every day is
the one that is never cached. `FIELD_AGENT_FIRST.md` line 818 recorded Shortest's caching as "not
documented"; it is now MEASURED as "not applied to the case that matters".

### Verdict

`RED_TEAM.md` §2.2 says "Architecture is not a moat — Shortest proves it", and that stands: they
built our shape and stopped. What the trial adds is that they never finished it. **Exit 0 on
failure** and **`**/*.test.ts` globbing `node_modules`** are not subtle regressions; they are what
you find in the first ten minutes, which means nobody has spent ten minutes with it in a while.
Steal the inline token/dollar line. Take the warning about the exit contract seriously enough to
keep testing ours.

## 4. Playwright's own agents (Microsoft, free) — **the healer is instructed to make the red go away**

`@playwright/test@1.62.1`. `npm install @playwright/test` → **1.0s**, 3 packages, **0
vulnerabilities**. `npx playwright init-agents --loop=claude` → **1.6s**:

```
 🎭 Using project "" as a primary project
 📝 specs/README.md - directory for test plans
 🌱 tests/seed.spec.ts - default environment seed file
 🤖 .claude/agents/playwright-test-generator.md - agent definition
 🤖 .claude/agents/playwright-test-healer.md - agent definition
 🤖 .claude/agents/playwright-test-planner.md - agent definition
 🔧 .mcp.json - mcp configuration
 ✅ Done.
```

**It writes seven files into your repo**, including `.claude/agents/` and `.mcp.json`. Note the
contrast with our positioning line ("nothing written to your repo") — theirs is the opposite bet,
and for a coding-agent user it is arguably the right one, because the artefacts *are* the product.

This is not a runner. It is three subagent definitions plus an MCP server that drive **your**
coding agent. The verdict is stock Playwright's.

### The failure output is Playwright's own (MEASURED)

The test the generator would write, run against the same bug:

```
  ✘  1 tests/checkout.spec.ts:5:5 › a shopper can check out (5.7s)

  1) tests/checkout.spec.ts:5:5 › a shopper can check out ────────────────────────

    Error: expect(locator).toBeVisible() failed

    Locator: getByText(/order (placed|confirmed)/i)
    Expected: visible
    Timeout: 5000ms
    Error: element(s) not found

    Call log:
      - Expect "toBeVisible" with timeout 5000ms
      - waiting for getByText(/order (placed|confirmed)/i)

    >  9 |   await expect(page.getByText(/order (placed|confirmed)/i)).toBeVisible();
    Error Context: test-results/checkout-a-shopper-can-check-out/error-context.md
```

**This is the honest baseline for the whole category and it deserves to be read carefully.** It is
precise, fast to parse, and tells you exactly what it looked for. And it never once tells you what
the page actually said. The words *"Something went wrong. Your order was not placed."* — the entire
bug — appear nowhere in the terminal. They are in `error-context.md`, in a YAML a11y dump, one file
open away.

It also burned **5 seconds of the 5.7** waiting for an element that was never going to appear.
Midscene and we both answer immediately, because we read the page rather than poll for an
expectation.

The gap between `element(s) not found` and `the page said "Something went wrong. Your order was not
placed."` is the entire product thesis, and it is now MEASURED on the same page and the same bug
rather than asserted.

### The finding that actually matters: what the healer is told to do

`.claude/agents/playwright-test-healer.md`, verbatim from the file Microsoft's CLI just wrote:

> - You will continue this process until the test runs successfully without any failures or errors.
> - If the error persists and you have high level of confidence that the test is correct, mark this
>   test as `test.fixme()` so that it is skipped during the execution.
> - Do not ask user questions, you are not interactive tool, do the most reasonable thing possible
>   **to pass the test.**

Its documented workflow step 5 is *"Code Remediation: Edit the test code to address identified
issues… Fixing assertions and expected values."*

**The free, first-party, zero-cost option in this category is a test-fixer, not a bug-finder.** Run
the healer against our shop app and its own instructions point at exactly two terminal states:
rewrite the assertion so `Something went wrong` is the expected text, or `test.fixme()` the test.
There is no path in that prompt that ends in *"your checkout is broken."*

**This sharpens `SCORECARD.md` row 11 and `FIELD_AGENT_FIRST.md`'s "authoring is being commoditized
to $0".** Both are right that Microsoft has made *authoring* free. Neither noticed that Microsoft's
*healing* is aimed at green, not at truth — which is not a commoditization of our value, it is the
opposite of it. The positioning line falls out of their own file: **anyone can make the test pass;
the question is whether the app works.** That sentence is now defensible with a quote from
Microsoft's shipped artefact, which is a much stronger place to argue from than a claim about
adjudication.

## 5. Stagehand (Browserbase, MIT) — **left the category, and is 21× leaner than Midscene**

`@browserbasehq/stagehand@4.0.2`, installed 2026-08-30. `npm install` → **4.2s**, 49 packages,
**0 vulnerabilities**, 33 MB.

### It is no longer a testing tool, in their own words

Their README, fetched today: *"Stagehand is the SDK for browser agents. **Playwright was built for
testing, Stagehand is built for agents.**"* (CLAIMED, and I take them at their word.) MEASURED
consequence: there is **no assertion, no verdict, no reporter, no exit code and no test file**
anywhere in the package. `FIELD_AGENT_FIRST.md` lists it among the agent-first tier; it should be
moved out of the competitive set and into "the driver a competitor might build on."

### The v4 API break

Every published quickstart — including in `AUTONOMA_IN_MOTION.md`-era material and most blog posts —
uses `stagehand.init()` and `stagehand.page.act()`. On 4.0.2 (MEASURED):

```
TypeError: sh.init is not a function
```
```
TypeError: Cannot read properties of undefined (reading 'goto')
```

The current shape is `await Stagehand.create({ browser, model })` with `localBrowser.launch()`, and
`page` comes off `browser.context`, not off Stagehand. Their own README's quickstart uses
`browserbase.launch({ apiKey })` — **the hosted service is the documented default path.**

### Two things that will bite anyone trying to run it locally

1. **`baseURL` is not accepted for OpenAI-compatible endpoints.** MEASURED: `ZodError … Unrecognized
   key: "baseURL"`. Reading `dist/index.mjs`, `baseURL` exists only on the **Vertex** and **Azure**
   provider option schemas. There is no supported way to point plain `openai/*` at a local or
   self-hosted endpoint.
2. **The provider call does not happen in Node.** Patching `globalThis.fetch` — which intercepts
   every other tool in this bakeoff — catches nothing. The error arrives through
   `RPCClient.receiveResponse` ← `CDPClient.handleMessage`: **the LLM call is made from inside the
   browser over CDP.** Anyone with an egress policy, a proxy, or a compliance review should know
   this before adopting it. Their escape hatch is a custom client, `model: { generate }`, which is
   how the run below was done.

### What it wrote into the repo

After roughly twenty runs including a 50-test suite: **28 KB, 3 files** —
`.smolanalytics/recordings/` (4 KB) and `.smolanalytics/evidence/` (24 KB, one PNG + one text file
for the one failure). Midscene's `midscene_run/` after a handful of runs of one test: **8.4 MB, 21
files**, growing ~2.8 MB per run with no retention policy. Playwright's `init-agents` writes
**seven files** including `.claude/agents/` and `.mcp.json`.

### The one thing that went wrong, reported rather than buried

On the seventh `--plan` replay of the `/ok` page — the first run that also carried `--share` — the
verdict was not `PASS` but:

```
The recorded steps still work, but the page no longer says "Order placed" — the text that proved
this test the last time it passed. That is either a regression or a reword, and a replay cannot
tell which. Handing it to the agent.
EXIT CODE = 2
```

The page was unchanged and served the proof text (verified by `curl` immediately afterwards). **It
did not reproduce: six controlled runs, three with `--share` and three without, all PASS / exit 0.**
So this is **one unexplained `stale` in seven runs of an unchanging page**, cause unknown,
**unverified** as a bug and explicitly not attributed to `--share`.

It matters anyway, for a reason the code makes clear: `settle()` in `lib/suite.mjs` only arbitrates
`passed`/`failed` attempts, so **a `stale` verdict is never retried.** A failure gets a second look
and says "Observed twice"; a one-off stale goes straight to exit 2 with no second look. If that
transient is real, it is a red CI job on a working app — the exact false-alarm class
`RED_TEAM.md` §"a suite people stop believing" is about. Worth a targeted soak test before anyone
quotes our replay reliability.

### 9.3 The three rows we win, stated as narrowly as they are true

1. **Replay with no key.** Ours is the only tool in this bakeoff that reaches a verdict on a real
   browser with no model reachable. Midscene is the only other tool with a portable local
   artefact, and its artefact **cannot execute a step without a live model connection** and bills a
   vision call per assertion forever. MEASURED both ways, §2 and §8.
2. **The exit-code contract, including a status for our own faults.** 1 = your app is broken,
   2 = we could not tell, 0 = pass. Two of the six others exit 0 on a failing test. Nobody else
   separates "our fault" from "your fault" at all — Midscene reports its own XML parse error as
   `Assertion failed`, and browser-use prints a pydantic traceback next to a correct verdict.
3. **The failure sentence, and everything printed around it** — the steps with reasons, the priced
   retry disclosure, `(Observed twice…)`, the evidence paths, and on the replay path a render guard
   that quotes a stack frame with zero model calls.

### 9.4 The rows we do not win, said plainly

- **Midscene's assertion reason is the shape to beat, not one we beat.** They got there first and
  their design decision — an `<observation>` field in the prompt, carried into the thrown error —
  is the one thing in this bakeoff worth copying outright.
- **Shortest prints tokens *and dollars* next to the test that spent them.** We print
  `6 model calls · 7,200 in / 360 out` and then instructions for how to configure dollars. Theirs is
  strictly better and costs us an afternoon.
- **Stagehand is leaner per step than we are** (12,261 vs 16,414 bytes) — because their per-call
  prompt is a trimmed a11y tree with no tool schema resent each turn. Our 2,484-byte tool schema and
  1,872-byte system prompt ride along on every call; at three calls that is 13,068 of our 16,414
  bytes, **80% fixed overhead**. On a twenty-step test the ratio inverts and we look fine; on short
  tests, which are most tests, it does not.
- **Playwright's authoring agents are free, first-party, and write artefacts the user owns.** Our
  "nothing written to your repo" line is a *different bet*, not a better one, and for a
  coding-agent user theirs is arguably right.
- **QA Wolf publishes an execution price** (15¢/runner-minute) and now has a self-serve tier. Free
  is table stakes in this category as of today, not a wedge.
